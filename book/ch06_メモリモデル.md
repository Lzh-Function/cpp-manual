## 6.1 メモリを方眼紙だと思う

コンピュータのメモリは、**番号のついたマス目が並んだ巨大な方眼紙**です。
1マス = 1バイト。マスの番号を **アドレス** と呼びます。

```
アドレス:  0x1000  0x1001  0x1002  0x1003  0x1004  0x1005 ...
          +-------+-------+-------+-------+-------+-------+
          |  2A   |  00   |  00   |  00   |  ??   |  ??   |
          +-------+-------+-------+-------+-------+-------+
          <------ int x = 42 (4バイト) ---->
```

`int x = 42;` と書くと、コンパイラは方眼紙のどこか4マスを `x` 用に割り当て、
そこに 42 のビットパターンを書き込みます。

**変数名は、コンパイル後には消えます。** 機械語には `x` という名前は存在せず、
「アドレス 0x1000 から4バイト」という情報だけが残ります。

実際に見てみましょう:

```cpp
#include <iostream>

int main() {
    int x = 42;
    std::cout << "value of x   : " << x  << "\n";
    std::cout << "address of x : " << &x << "\n";   // & でアドレスを取得
    std::cout << "size of x    : " << sizeof(x) << " bytes\n";
}
```

```
value of x   : 42
address of x : 0x7ffd3a2c4b5c
size of x    : 4 bytes
```

> 🐍 **Pythonとの対比**
>
> Pythonの `id(x)` がアドレスに相当します。
> ```python
> x = 42
> print(id(x))   # 140234... （CPython ではオブジェクトのアドレス）
> ```
> ただしPythonの `id()` は**オブジェクトのアドレス**。
> C++の `&x` は**変数そのもののアドレス**です。ここが決定的に違います。

## 6.2 スタックとヒープ

プログラムが使うメモリは、用途別に区画分けされています。

```
高位アドレス
    +--------------------------------+
    |         スタック (Stack)        |  <- 関数のローカル変数。自動管理。速い
    |            ↓ 下に伸びる          |     サイズは 1〜8MB 程度
    +--------------------------------+
    |                                |
    |         (未使用領域)             |
    |                                |
    +--------------------------------+
    |            ↑ 上に伸びる          |
    |         ヒープ (Heap)           |  <- new/malloc で確保。手動管理。遅い
    |                                |     サイズは物理メモリまで
    +--------------------------------+
    |     静的領域 (Static/BSS)       |  <- グローバル変数、static 変数
    +--------------------------------+
    |     コード領域 (Text)           |  <- 機械語そのもの
    +--------------------------------+
低位アドレス
```

### スタック

```cpp
void f() {
    int a = 1;          // スタックに4バイト確保
    double b = 2.0;     // スタックに8バイト確保
    char c[100];        // スタックに100バイト確保
}                       // ★ 関数を抜けると全部まとめて解放（一瞬）
```

**スタックの特徴:**

| 項目 | 内容 |
|---|---|
| 確保速度 | **超高速**（スタックポインタを動かすだけ。1命令） |
| 解放 | **自動**。スコープを抜けたら勝手に消える |
| サイズ | 小さい（Linux 8MB、Windows 1MB がデフォルト） |
| 寿命 | そのスコープの間だけ |
| 連続性 | 連続。**キャッシュに乗りやすい** |

スタックは「積み木」です。関数を呼ぶたびに上に積み、
帰るたびに上から降ろします。だから **Stack**（積み重ね）。

```
main() を実行中:
    +-------------+
    | main のローカル変数 |
    +-------------+

main() から f() を呼んだ:
    +-------------+
    | f のローカル変数    |  <- 新しく積まれた
    +-------------+
    | 戻り先アドレス      |
    +-------------+
    | main のローカル変数 |
    +-------------+

f() から帰った:
    +-------------+
    | main のローカル変数 |  <- f の分は一瞬で消えた
    +-------------+
```

> ⚠️ **スタックオーバーフロー**
>
> ```cpp
> void f() {
>     double huge[10'000'000];   // 80MB をスタックに！ → クラッシュ
> }
> ```
> ```cpp
> void recurse(int n) { recurse(n + 1); }   // 無限再帰 → クラッシュ
> ```
> 大きなデータはヒープ（= `std::vector`）に置いてください。

### ヒープ

```cpp
void f() {
    std::vector<double> v(10'000'000);   // 80MB をヒープに確保
}                                        // vector のデストラクタが解放してくれる
```

**ヒープの特徴:**

| 項目 | 内容 |
|---|---|
| 確保速度 | **遅い**（数十〜数百サイクル。空き領域を探す必要がある） |
| 解放 | **手動**（ただしvectorやスマートポインタが自動化してくれる） |
| サイズ | 大きい（物理メモリ/仮想メモリの限界まで） |
| 寿命 | 明示的に解放するまで |
| 断片化 | 起きる。長時間動かすと性能劣化することも |

> 💡 **原則: できるだけスタックを使え**
>
> スタック確保は事実上タダです。ヒープ確保（`malloc`）は
> **数百サイクル**かかることがあります。
> ループの中で毎回 `std::vector` を作るコードは、それだけで遅くなります。
>
> ```cpp
> // ✗ 遅い: 毎回ヒープ確保・解放
> for (const auto& mol : mols) {
>     std::vector<int> buf(1000);
>     compute(mol, buf);
> }
>
> // ✓ 速い: 1回だけ確保して使い回す
> std::vector<int> buf(1000);
> for (const auto& mol : mols) {
>     std::fill(buf.begin(), buf.end(), 0);
>     compute(mol, buf);
> }
> ```
> これで数倍速くなることがあります。第28章で詳しく。

### 🐍 Pythonは全部ヒープ

```python
x = 42
```

Pythonでは、この `42` も**ヒープ上のオブジェクト**です。
だからPythonは「メモリ確保のコスト」を常に払っています
（小さい整数はキャッシュされていますが、原則は同じ）。

C++で `int x = 42;` はスタック上の4バイト。確保コストは実質ゼロ。
これが第1章で見た100倍の差の一部です。

## 6.3 ポインタ

さあ、本題です。

### ポインタとは「アドレスを入れる変数」

```cpp
int x = 42;
int* p = &x;    // p は「x のアドレス」を保持する変数
```

```
        メモリ
        +----------+----------+
アドレス | 0x1000   | 0x2000   |
        +----------+----------+
 内容   |   42     | 0x1000   |
        +----------+----------+
        変数 x      変数 p
        (int)      (int*)
                      │
                      └──────┐
                             ▼
                        「x を指している」
```

- `&x` … x のアドレスを取り出す（**アドレス演算子**）
- `int*` … 「int を指すポインタ」という型
- `*p` … p が指す先の値を取り出す（**間接参照 / デリファレンス**）

```cpp
int x = 42;
int* p = &x;

std::cout << x   << "\n";   // 42     x の値
std::cout << &x  << "\n";   // 0x1000 x のアドレス
std::cout << p   << "\n";   // 0x1000 p の値（= x のアドレス）
std::cout << *p  << "\n";   // 42     p の指す先の値
std::cout << &p  << "\n";   // 0x2000 p 自身のアドレス

*p = 100;                   // p の指す先に書き込む
std::cout << x   << "\n";   // 100    x が変わった！
```

> 💡 **`*` の読み方**
>
> `int* p;` の `*` は「型の一部」（int へのポインタ型）。
> `*p` の `*` は「演算子」（指す先を取り出す）。
>
> 同じ記号で意味が違うのが混乱の元です。
> **宣言では型、式では演算子**と覚えてください。

### なぜポインタが必要なのか

理由は3つです。

**① 関数から呼び出し元の変数を書き換えるため**

```cpp
void increment(int x)  { x += 1; }      // ✗ コピーなので効果なし
void increment(int* p) { *p += 1; }     // ✓ 呼び出し元が変わる

int a = 5;
increment(a);    // a は 5 のまま
increment(&a);   // a が 6 になる
```

**② 大きなデータをコピーせずに渡すため**

```cpp
void process(const Molecule* mol);   // ポインタ8バイトだけ渡る
```

**③ 動的に確保したメモリを扱うため**

```cpp
int* arr = new int[1000];   // ヒープに確保。arr がその先頭を指す
// ... 使う ...
delete[] arr;               // 解放
```

ただし、**現代C++では ① と ② は参照で、③ は vector / スマートポインタでやります。**
つまり、**生ポインタを書く機会はほとんどありません**（後述）。

### ポインタ演算

ポインタに整数を足すと、**型のサイズ分だけ**進みます。

```cpp
int arr[5] = {10, 20, 30, 40, 50};
int* p = arr;        // 配列名は先頭要素のポインタに変換される

std::cout << *p     << "\n";   // 10
std::cout << *(p+1) << "\n";   // 20  ← 4バイト進む（int のサイズ）
std::cout << *(p+2) << "\n";   // 30
std::cout << p[2]   << "\n";   // 30  ← *(p+2) と全く同じ意味！
```

```
       +------+------+------+------+------+
       |  10  |  20  |  30  |  40  |  50  |
       +------+------+------+------+------+
       0x1000 0x1004 0x1008 0x100C 0x1010
         ▲      ▲      ▲
         p     p+1    p+2
```

**`p[i]` は `*(p + i)` の糖衣構文**です。配列の添字アクセスの正体がこれです。

> ⚠️ **だから配列の範囲チェックが存在しない**
>
> ```cpp
> int arr[5];
> arr[100] = 1;   // ★ コンパイルも実行も通る。しかし他人のメモリを破壊
> ```
> `arr[100]` は「arr の先頭から400バイト先に書き込む」という意味でしかありません。
> そこに何があるかは知ったことではないのです。
>
> Pythonなら `IndexError` が出ます。C++は**黙って壊します**。
> これがC++が「危険」と言われる最大の理由です。
>
> **対策**: 生配列を使わず `std::vector` / `std::array` を使い、
> デバッグ時は `-fsanitize=address` を付ける（第29章）。

### nullptr — 「どこも指していない」

```cpp
int* p = nullptr;      // 何も指していない
if (p != nullptr) {
    *p = 1;            // 安全にチェックしてから使う
}
*p = 1;                // ★ nullptr をデリファレンス → Segmentation fault
```

Pythonの `None` に近い概念です。

> ⚠️ 古いコードでは `NULL` や `0` を使います。
> **`nullptr` を使ってください**（型安全で、オーバーロードの曖昧さを避けられます）。

**セグメンテーション違反 (Segfault) の正体**は、
だいたい「nullptrか、解放済みか、範囲外のアドレスにアクセスした」です。

## 6.4 参照

参照は「**別名 (alias)**」です。ポインタより簡単で安全です。

```cpp
int x = 42;
int& r = x;      // r は x の別名。r と x は「同じもの」

r = 100;
std::cout << x << "\n";   // 100
std::cout << r << "\n";   // 100
std::cout << &x << " " << &r << "\n";   // ★ 同じアドレス！
```

```
        +----------+
アドレス | 0x1000   |
        +----------+
 内容   |   100    |
        +----------+
         ↑      ↑
         x      r      ← 同じ場所に2つの名前が付いているだけ
```

### ポインタとの違い

| 項目 | ポインタ `int*` | 参照 `int&` |
|---|---|---|
| 初期化 | 後でもよい | **宣言時に必須** |
| 「無」を表せる | `nullptr` | **不可** |
| 指す先の変更 | できる | **できない**（一度決めたら固定） |
| デリファレンス | `*p` が必要 | 不要。そのまま使える |
| アドレス演算 | できる | できない |
| 安全性 | 低い | **高い** |

```cpp
int a = 1, b = 2;

int* p = &a;
p = &b;          // ✓ 指す先を変更できる

int& r = a;
r = b;           // ★ これは「a に b の値を代入」であって、指す先の変更ではない！
                 //    a == 2 になる
```

> ⚠️ **参照の再束縛はできません。** `r = b;` は代入です。
> これは初心者が必ず一度は勘違いするポイントです。

### 🐍 Pythonの変数は「参照」に近い

```python
a = [1, 2, 3]
b = a          # b は a と同じリストを指す
b.append(4)
print(a)       # [1, 2, 3, 4]  ← a も変わった
```

```cpp
std::vector<int> a = {1, 2, 3};
std::vector<int>& b = a;    // 参照
b.push_back(4);
// a は {1,2,3,4}
```

**Pythonの変数代入は、C++の参照に近い**のです。
逆に、C++のデフォルト（`std::vector<int> b = a;`）は**ディープコピー**です。

```cpp
std::vector<int> a = {1, 2, 3};
std::vector<int> b = a;     // ★ 中身が全部コピーされる（Python の copy.deepcopy 相当）
b.push_back(4);
// a は {1,2,3} のまま
```

> 💡 **ここが一番の意識の切り替えポイント**
>
> | | Python | C++ |
> |---|---|---|
> | `b = a` | 参照のコピー（同じ実体） | **値のコピー（別の実体）** |
> | 参照が欲しい | デフォルト | `&` を明示 |
> | コピーが欲しい | `copy.deepcopy(a)` | デフォルト |
>
> **C++はデフォルトが「値」**です。だから明示的に `&` を書く必要があるのです。
> そしてこれが第5章の「引数渡し」の話に直結します。

### 関数引数としての参照

```cpp
void f(int x)  { x = 100; }   // 値渡し。呼び出し元は変わらない
void g(int& x) { x = 100; }   // 参照渡し。呼び出し元が変わる

int a = 1;
f(a);   // a == 1
g(a);   // a == 100  ← 呼び出し側の見た目は同じ！
```

> ⚠️ **呼び出し側では区別がつきません。**
> ポインタなら `g(&a)` と書くので「これは変わるかも」と分かりますが、
> 参照だと `g(a)` です。
>
> **だからこそ `const&` が重要**です。
> `const T&` なら変わらないと保証されるので、読み手が安心できます。
>
> Googleのスタイルガイドは長らく「出力引数はポインタで渡せ」としていました
> （呼び出し側に `&` が見えるから）。今は参照も許容されています。
> チームのルールに従ってください。

### const参照は一時オブジェクトも束縛できる

```cpp
void f(const std::string& s);

f("CCO");              // ✓ 一時的な std::string が作られ、const& が束縛
                       //   （寿命は f の呼び出しが終わるまで延長される）

void g(std::string& s);
g("CCO");              // ✗ エラー: 非constの参照は一時オブジェクトを束縛できない
```

これも `const&` を使うべき理由のひとつです。

## 6.5 ⚠️ ダングリング参照/ポインタ

**C++で最も危険なバグ**です。

```cpp
int* bad() {
    int x = 42;
    return &x;      // ★ x はこの関数を抜けたら消える！
}                   //   返されたポインタは「もう存在しない場所」を指す

int main() {
    int* p = bad();
    std::cout << *p;   // ★ 未定義動作。たまたま動くこともあるのが最悪
}
```

```cpp
const std::string& bad2() {
    std::string s = "CCO";
    return s;       // ★ 同じ問題
}
```

```cpp
std::vector<int> v = {1,2,3};
int& r = v[0];
v.push_back(4);     // ★ 再確保が起きると、v の中身は別のアドレスに引っ越す
std::cout << r;     // ★ r は古いアドレスを指している = ダングリング
```

> ⚠️ **鉄則: ローカル変数への参照/ポインタを返してはいけない**
>
> コンパイラは `-Wall` で警告してくれることが多いですが、
> 間接的な場合は検出できません。
>
> **対策:**
> - 値を返す（C++は最適化でコピーを消してくれる。RVO/ムーブ。第12章）
> - vector を変更した後は、以前に取った参照・ポインタ・イテレータを使わない
> - `-fsanitize=address` でテストする（第29章）

**正しい書き方:**

```cpp
std::string good() {
    std::string s = "CCO";
    return s;       // ✓ 値で返す。コピーは最適化で消える（NRVO）
}
```

「値を返すとコピーが起きて遅いのでは?」と心配になりますが、
**心配無用です**。コンパイラが `s` を直接呼び出し元の場所に構築します（RVO）。
第12章で詳しく説明します。

## 6.6 `new` と `delete`（読めれば十分）

古いコードや、ライブラリの内部で見かけます。

```cpp
int* p = new int(42);       // ヒープに int を1個確保
delete p;                   // 解放

int* arr = new int[100];    // ヒープに int を100個確保
delete[] arr;               // ★ 配列は delete[] （[] を忘れると未定義動作）

Molecule* m = new Molecule("CCO");
delete m;
```

**問題点:**

1. **解放忘れ = メモリリーク**
   ```cpp
   int* p = new int(42);
   return;   // ★ delete し忘れた。永久にメモリが返らない
   ```

2. **例外が飛ぶとリーク**
   ```cpp
   int* p = new int(42);
   may_throw();     // ★ ここで例外が飛ぶと delete が実行されない
   delete p;
   ```

3. **二重解放 = クラッシュ**
   ```cpp
   delete p;
   delete p;        // ★ 未定義動作
   ```

4. **解放後の使用 (use-after-free)**
   ```cpp
   delete p;
   *p = 1;          // ★ 未定義動作。セキュリティ脆弱性の温床
   ```

### 💡 だから現代C++では `new` を書きません

| やりたいこと | 昔 | 今 |
|---|---|---|
| 動的配列 | `new int[n]` / `delete[]` | **`std::vector<int>`** |
| 単一オブジェクトの動的確保 | `new T` / `delete` | **`std::make_unique<T>()`** |
| 共有されるオブジェクト | 手動参照カウント | **`std::make_shared<T>()`** |
| 文字列 | `new char[n]` | **`std::string`** |

```cpp
// 昔
Molecule* m = new Molecule("CCO");
process(m);
delete m;

// 今
auto m = std::make_unique<Molecule>("CCO");
process(*m);
// スコープを抜けたら自動的に delete される
```

第13章でスマートポインタを扱います。それまで `new` は書かなくて大丈夫です。

## 6.7 メモリレイアウトとキャッシュ（性能の話）

ここは第23章・第28章の伏線ですが、今のうちに感覚を作っておきましょう。

### CPUキャッシュの階層

```
   CPU コア
      │  1サイクル
   +--------+
   | レジスタ |   ~数十バイト
   +--------+
      │  ~4サイクル
   +--------+
   |  L1    |   32〜64 KB
   +--------+
      │  ~12サイクル
   +--------+
   |  L2    |   256KB〜1MB
   +--------+
      │  ~40サイクル
   +--------+
   |  L3    |   8〜32MB（コア間で共有）
   +--------+
      │  ~200サイクル ★ 圧倒的に遅い
   +--------+
   | メインメモリ |   GB オーダー
   +--------+
```

**メインメモリへのアクセスは、L1キャッシュの50倍遅い**のです。
CPUは200サイクル、つまり足し算200回分の時間を待たされます。

### キャッシュラインという単位

CPUはメモリを1バイトずつ読みません。**64バイト単位**（キャッシュライン）で読みます。

```cpp
std::vector<int> v(1000);
int s = 0;
for (int x : v) s += x;    // 連続アクセス
```

`v[0]` を読むとき、CPUは `v[0]`〜`v[15]`（64バイト = int 16個）を
まとめてキャッシュに載せます。だから次の15回は**キャッシュヒット**で超高速です。

```
メモリからの1回の読み込み（64バイト）
+----+----+----+----+----+----+----+----+ ... +----+
| v0 | v1 | v2 | v3 | v4 | v5 | v6 | v7 |     |v15 |
+----+----+----+----+----+----+----+----+ ... +----+
  ▲
  1回だけメモリ待ち。残り15個はタダ
```

対して、ポインタで散らばったデータは:

```cpp
std::vector<Molecule*> mols;   // ポインタの配列
for (auto* m : mols) s += m->mw();   // ★ 毎回別の場所へジャンプ
```

```
 mols[0] -> 0x8A31000  (キャッシュミス、200サイクル待ち)
 mols[1] -> 0x1F02840  (キャッシュミス、200サイクル待ち)
 mols[2] -> 0xC739180  (キャッシュミス、200サイクル待ち)
```

**これがPythonのリストが遅い、もうひとつの理由です。**
Pythonのリストは常にポインタの配列だからです。

> 🧪 **ケモインフォマティクスでの実例**
>
> 100万分子のフィンガープリント（各256バイト）を持つとき:
>
> ```cpp
> // ✗ 遅い: ポインタの配列。データが散らばる
> std::vector<Fingerprint*> fps;
>
> // ✓ 速い: 値の配列。256MB が連続配置される
> std::vector<Fingerprint> fps;
>
> // ✓✓ 最速: 1本の巨大配列にフラット化
> std::vector<std::uint64_t> flat_fps;   // 32 * 1'000'000 個
> // i番目の分子は flat_fps[i*32] から 32 word
> ```
>
> 3番目の書き方が第23章で使う手法です。実測で2〜3倍変わります。

## 6.8 全体像: いつ何を使うか

```
    データを扱いたい
          │
    サイズはコンパイル時に分かる?
          │
    ┌─────┴─────┐
   Yes          No
    │            │
  小さい?    std::vector<T>  ← ほぼ常にこれ
    │
 ┌──┴──┐
Yes    No（数MB以上）
 │      │
std::array<T,N>   std::vector<T>
（スタック）        （ヒープ）
```

```
    オブジェクトを1個、動的に持ちたい
          │
    所有者は1人?
          │
    ┌─────┴─────┐
   Yes          No（複数で共有）
    │            │
std::unique_ptr  std::shared_ptr
```

```
    関数に渡したい
          │
    書き換える?
          │
    ┌─────┴─────┐
   Yes          No
    │            │
   T&        重い型?
              │
        ┌─────┴─────┐
       Yes          No
        │            │
     const T&        T（値渡し）
```

**生ポインタ `T*` を使うのは、「所有権を持たない、nullかもしれない参照」を
表したいときだけ**です。それ以外の用途はすべて上の道具でカバーできます。

## 6.9 🧪 実践: メモリレイアウトを実測する

```cpp
// code/ch06/cache_bench.cpp
#include <chrono>
#include <iostream>
#include <memory>
#include <numeric>
#include <random>
#include <vector>

struct Timer {
    std::chrono::steady_clock::time_point t0 = std::chrono::steady_clock::now();
    double ms() const {
        auto t1 = std::chrono::steady_clock::now();
        return std::chrono::duration<double, std::milli>(t1 - t0).count();
    }
};

int main() {
    constexpr std::size_t N = 5'000'000;

    // --- ① 連続した値の配列 ---
    std::vector<double> flat(N);
    std::iota(flat.begin(), flat.end(), 1.0);

    // --- ② ポインタの配列（Python のリスト相当）---
    std::vector<std::unique_ptr<double>> scattered;
    scattered.reserve(N);
    for (std::size_t i = 0; i < N; ++i)
        scattered.push_back(std::make_unique<double>(static_cast<double>(i + 1)));

    // ポインタをシャッフルして、さらにキャッシュに不利にする
    std::mt19937 rng(42);
    std::shuffle(scattered.begin(), scattered.end(), rng);

    {
        Timer t;
        double sum = 0;
        for (double x : flat) sum += x;
        std::cout << "contiguous : " << t.ms() << " ms  (sum=" << sum << ")\n";
    }
    {
        Timer t;
        double sum = 0;
        for (const auto& p : scattered) sum += *p;
        std::cout << "scattered  : " << t.ms() << " ms  (sum=" << sum << ")\n";
    }
}
```

```bash
g++ -std=c++20 -O2 cache_bench.cpp -o cache_bench
./cache_bench
```

手元の結果（環境により変わります）:

```
contiguous : 4.2 ms  (sum=1.25e+13)
scattered  : 118.6 ms  (sum=1.25e+13)
```

**同じ計算が28倍違います。** アルゴリズムは全く同じで、
違うのは**メモリのどこにデータがあるか**だけです。

これがC++でパフォーマンスを出すために最も重要な感覚です。

## 6.10 この章のまとめ

- メモリは番号付きのマス目。変数はその一区画。`&x` でアドレスが取れる
- **スタック**: ローカル変数。自動解放、超高速、サイズ小
- **ヒープ**: 動的確保。手動解放（vectorが代行）、遅い、サイズ大
- **ポインタ `T*`**: アドレスを保持する変数。`*p` で中身、`p[i]` は `*(p+i)`
- **参照 `T&`**: 別名。初期化必須、null不可、再束縛不可、**安全**
- **Pythonの `b = a` は参照、C++の `b = a` はコピー** ← 最重要の意識切り替え
- ローカル変数への参照/ポインタを返すな（ダングリング）
- `new`/`delete` は書かない。vector とスマートポインタを使う
- **メモリの連続性がキャッシュ効率を決め、数十倍の性能差になる**

### 覚えるべき記号の意味

| 記号 | 文脈 | 意味 |
|---|---|---|
| `&x` | 式の中 | x のアドレスを取る |
| `int& r` | 宣言 | 参照型 |
| `*p` | 式の中 | p の指す先 |
| `int* p` | 宣言 | ポインタ型 |
| `p->m` | 式の中 | `(*p).m` の略記 |
| `.` | 式の中 | メンバアクセス（値・参照に対して） |
