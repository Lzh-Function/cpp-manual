# 第1章 なぜPython使いがC++を学ぶのか

## 1.1 まず、実物を見てもらう

Tanimoto係数の計算を考えます。ケモインフォマティクスで最も頻繁に呼ばれる関数のひとつです。

2つのビットベクタ（フィンガープリント）A, B に対して:

```
                |A ∩ B|         c
T(A, B) = ---------------- = ---------
                |A ∪ B|       a + b - c
```

ここで a = |A|（Aで立っているビット数）、b = |B|、c = |A ∩ B|（両方で立っているビット数）です。

### Pythonでの素直な実装

```python
# 2048ビットのフィンガープリントを、bool のリストで表現
def tanimoto(a: list[bool], b: list[bool]) -> float:
    common = 0
    only_a = 0
    only_b = 0
    for x, y in zip(a, b):
        if x and y:
            common += 1
        elif x:
            only_a += 1
        elif y:
            only_b += 1
    denom = common + only_a + only_b
    return common / denom if denom else 0.0
```

これを 10,000 × 10,000 ペア（1億回）実行すると、手元の環境で **約 3.5 時間**。

### C++での素直な実装

```cpp
#include <array>
#include <cstddef>

double tanimoto(const std::array<bool, 2048>& a,
                const std::array<bool, 2048>& b) {
    int common = 0, only_a = 0, only_b = 0;
    for (std::size_t i = 0; i < a.size(); ++i) {
        if (a[i] && b[i])   ++common;
        else if (a[i])      ++only_a;
        else if (b[i])      ++only_b;
    }
    int denom = common + only_a + only_b;
    return denom ? static_cast<double>(common) / denom : 0.0;
}
```

**同じアルゴリズム、同じ論理**です。これが約 **2分**。**約100倍**速い。

### さらに、C++らしく書くと

ビットを1個ずつ見るのをやめ、64ビットまとめて扱います（第22章で詳説）:

```cpp
#include <array>
#include <bit>       // C++20: std::popcount
#include <cstdint>

using FP = std::array<std::uint64_t, 32>;  // 32 * 64 = 2048 bit

double tanimoto(const FP& a, const FP& b) {
    int inter = 0, uni = 0;
    for (std::size_t i = 0; i < 32; ++i) {
        inter += std::popcount(a[i] & b[i]);
        uni   += std::popcount(a[i] | b[i]);
    }
    return uni ? static_cast<double>(inter) / uni : 0.0;
}
```

これが **約 1.1 秒**。最初のPythonから **約 11,000 倍**。

| 実装 | 1億ペアの所要時間 | 相対速度 |
|---|---|---|
| Python (list of bool) | 約 3.5 時間 | 1x |
| Python + NumPy (packbits + ビット演算) | 約 25 秒 | 500x |
| C++ 素直な実装 | 約 2 分 | 105x |
| C++ ビット並列 + popcount | 約 1.1 秒 | 11,000x |
| C++ + AVX2 + マルチスレッド | 約 0.15 秒 | 84,000x |

> ⚠️ **注意**: NumPy版が速いのは、内部が**すでにC**だからです。
> 「Pythonが遅い」のではなく「**Pythonのループ**が遅い」のです。
> だからNumPy/RDKitで済む処理は素直にそれを使うべきです。
> C++が必要になるのは、**NumPyでベクトル化できない処理**のときです。

## 1.2 なぜPythonのループは遅いのか

ここを理解すると、C++の全設計が「なるほど」になります。

### Pythonの `a = 3` で起きていること

```python
a = 3
```

CPythonの内部では、こうなっています（概念図）:

```
       名前空間（辞書）                  ヒープ（オブジェクトの海）
    +----------------+           +------------------------------+
    | "a" -> 0x7f3a  | --------> | 0x7f3a: PyLongObject         |
    +----------------+           |   ob_refcnt : 1  (参照カウント) |
                                 |   ob_type   : &PyLong_Type   |
                                 |   ob_size   : 1              |
                                 |   ob_digit  : [3]            |
                                 +------------------------------+
                                       合計 28 バイト
```

**整数の 3 を保持するのに 28 バイト**使います。しかも実体はヒープ上の別の場所にあり、
変数 `a` はそこへの**ポインタ**です。

実際に確認できます:

```python
>>> import sys
>>> sys.getsizeof(3)
28
>>> sys.getsizeof(10**100)
72
```

### `a + b` で起きていること

```python
c = a + b
```

CPythonのバイトコードは `BINARY_ADD`（3.11以降は `BINARY_OP`）1命令ですが、
その1命令の中で以下が起きます:

1. `a` のポインタを辿ってオブジェクトを取得
2. `a` の型を調べる（`ob_type` を見る）
3. その型の `nb_add` スロット（加算関数）を探す
4. `b` についても同じことをする
5. 型の組み合わせが有効か確認する（`int + int`? `int + str`?）
6. **新しい** `PyLongObject` をヒープに確保する（メモリアロケータ呼び出し）
7. 足し算を実行 ← **ここが本来やりたかったこと。CPUにとっては1サイクル**
8. 参照カウントを更新する
9. 結果のポインタを `c` の名前空間エントリに格納する

**本来1サイクルの仕事に、数百サイクル**かかります。
オーバーヘッドの正体は「**型が実行時まで分からないこと**」と
「**すべてがヒープ上のオブジェクトであること**」の2つです。

### C++の `int a = 3;` で起きていること

```cpp
int a = 3;
int b = 5;
int c = a + b;
```

```
       スタック（関数のローカル領域）
    +------------+------------+------------+
    | a:  3      | b:  5      | c:  8      |
    | (4バイト)   | (4バイト)   | (4バイト)   |
    +------------+------------+------------+
```

- **4バイト**。ヒープ確保なし。ポインタの間接参照なし。
- 型はコンパイル時に分かっているので、実行時の型チェックはゼロ。
- `a + b` は**機械語1命令**（x86なら `add`）。
- しかも変数はCPUのレジスタに載る可能性が高く、メモリアクセスすら発生しないことがある。
- 上の例なら、コンパイラは `c = 8` と**コンパイル時に計算**してしまうことすらある。

これが100倍の正体です。

> 🐍 **Pythonとの対比**
>
> Pythonは「あらゆる値が、型情報と参照カウントを背負ったヒープ上の箱」。
> C++は「値はそのままメモリに置く。型はコンパイル時に決まっていて実行時には消える」。
>
> C++で `int` が4バイトなのは、**4バイトの整数そのもの**だからです。
> メタデータが一切付いていません。こういう「素の値」を **POD (Plain Old Data)** と呼びます。

### リストの違いも決定的

```python
xs = [1, 2, 3]
```

```
   PyListObject
   +----------------+          +----------+
   | ob_item  ------+--------> | 0x1000  -+--> PyLongObject(1)  28バイト
   | ob_size:     3 |          | 0x2000  -+--> PyLongObject(2)  28バイト
   | allocated:   4 |          | 0x3000  -+--> PyLongObject(3)  28バイト
   +----------------+          +----------+
                              ポインタ配列(8バイト x 3)
```

合計およそ 56（ヘッダ）+ 32（ポインタ配列）+ 84（整数3つ）= **約172バイト**。
しかも整数の実体は**メモリ上でバラバラの場所**にあります。

```cpp
std::vector<int> xs = {1, 2, 3};
```

```
   std::vector<int>
   +----------------+          +----+----+----+
   | data  ---------+--------> | 1  | 2  | 3  |  <- 連続した12バイト
   | size:       3  |          +----+----+----+
   | capacity:   3  |
   +----------------+
```

合計 24（ヘッダ）+ 12（データ）= **36バイト**。しかもデータは**連続**。

この「連続していること」が、後で説明する**キャッシュ効率**で圧倒的な差を生みます
（第7章、第23章、第28章）。ざっくり言うと、CPUはメモリから64バイト単位でデータを
まとめて読むので、連続していれば1回の読み込みで `int` が16個手に入ります。
バラバラなら1個ずつ、しかも毎回200サイクル待たされます。

### GIL の話も一応

Pythonにはグローバルインタプリタロック (GIL) があり、
純Pythonコードは複数スレッドで同時実行できません（3.13の free-threading ビルドを除く）。

C++には当然そんな制約はありません。16コアあれば16倍（に近い）並列化ができます（第25章）。
しかもC++側で処理している間はGILを解放できるので、
**「Pythonから呼ばれるC++関数の中で16スレッド回す」**が普通にできます（第26章）。

## 1.3 じゃあ、いつC++を使うべきか

C++に書き換えるべきかどうかの判断フローチャート:

```
        あなたの処理は遅い?
              |
        +-----+-----+
       No          Yes
        |            |
     使うな    NumPy/pandas/RDKitでベクトル化できる?
                     |
              +------+------+
             Yes           No
              |             |
        それでやれ    処理は「単純な計算の繰り返し」?
                            |
                     +------+------+
                    Yes           No (I/O待ちが支配的)
                     |             |
              Numba/Cythonで済む?  非同期/並列I/Oを検討
                     |
              +------+------+
             Yes           No
              |             |
         それでやれ    ★ C++の出番 ★
```

### 🧪 ケモインフォマティクスで C++ が効く場面

| 場面 | 理由 |
|---|---|
| **大規模類似度検索**（1M〜1B化合物） | ビット演算 + SIMD + マルチスレッド。NumPyでは限界がある |
| **グラフアルゴリズム**（部分構造検索、MCS、環検出） | 再帰・バックトラッキングが多くベクトル化不能 |
| **コンフォマー生成 / 力場計算** | 反復計算の塊。ML力場の推論ループも |
| **自作フィンガープリント/記述子** | RDKitに無いものを高速に |
| **モンテカルロ・シミュレーション** | 逐次依存でベクトル化不能 |
| **データローダのホットパス** | PyTorch DataLoader がボトルネックのとき |
| **既存C++資産の利用** | RDKit本体, Open Babel, OpenMM, xtb, LAMMPS はすべてC++ |
| **メモリに乗り切らないデータ** | mmap、ストリーミング、独自バイナリ形式 |

### ⚠️ C++を使うべきでない場面

- **一度きりの解析スクリプト** — 開発時間の方が高くつく
- **I/O待ちが支配的な処理** — CPU速度は関係ない
- **NumPy一発で書ける処理** — 既にCで動いている
- **プロトタイピング段階** — 設計が固まる前にC++にすると死ぬ
- **チームに自分しかC++を書けない** — 保守が地獄になる

> 💡 **実務のコツ**
>
> 「全部C++で書き直す」は99%失敗します。
> **Pythonのプロファイルを取り、上位1〜2関数だけをC++に落とす**のが正解です。
> 第26章の pybind11 を使えば、C++で書いた関数を `import` して使えます。
> Pythonの快適さを1ミリも捨てずに、遅い部分だけ100倍速くできます。
>
> RDKit自身がまさにこの構造です。あなたが毎日書いている
> `Chem.MolFromSmiles()` は、実体はC++の `RDKit::SmilesToMol()` です。

## 1.4 「C++は難しい」の正体

正直に言うと、C++は難しいです。ただし、難しさの中身を分解すると:

| 難しさの種類 | 実際の重さ | 対処 |
|---|---|---|
| メモリ管理（手動 new/delete） | **昔は重かった。今は軽い** | スマートポインタと vector で消える（第13章） |
| ポインタ | 概念は1時間で分かる | 第6章で絵を描いて説明します |
| コンパイルエラーが読めない | 最初はきつい | 付録Bで辞典を用意しました |
| ビルドシステム（CMake） | 地味に重い | 第19章でテンプレートを渡します |
| テンプレートメタプログラミング | **本当に難しい** | **書かなくていい**。読めれば十分 |
| 言語仕様の膨大さ | 全部知る必要はない | 実務で使うのは2割 |
| 未定義動作 (UB) | 危険 | サニタイザで自動検出（第29章） |

つまり、**「C++の難しい部分の大半は、モダンC++では避けられる」**のです。

1998年のC++ と 2020年のC++ は、ほぼ別言語です。この本は後者だけを教えます。

### 昔のC++ vs 今のC++

```cpp
// 1998年のC++（今は書かない）
Molecule* mol = new Molecule();
mol->parse(smiles);
std::vector<Atom*>* atoms = mol->getAtoms();
for (std::vector<Atom*>::iterator it = atoms->begin();
     it != atoms->end(); ++it) {
    std::cout << (*it)->getSymbol() << std::endl;
}
delete mol;   // 忘れるとリーク。例外が飛ぶとやはりリーク
```

```cpp
// 2020年のC++（この本で教える書き方）
auto mol = parse_smiles(smiles);        // 戻り値で受ける。deleteは不要
for (const auto& atom : mol.atoms()) {  // range-based for
    std::println("{}", atom.symbol());  // C++23 (C++20なら std::format)
}
// スコープを抜けたら自動的に解放される
```

行数が半分、`delete` が消え、読みやすく、**しかも同じかそれ以上に速い**。

## 1.5 C++の哲学: ゼロオーバーヘッド原則

C++の設計者 Bjarne Stroustrup の有名な言葉:

> **使わない機能にはコストを払わない。使う機能は、手書きしたのと同等以上に速い。**

具体例:

- 例外を使わないコードには、例外のコストがかからない
- `std::vector` は、自分で malloc して書いた配列と**同じ速度**
- `std::sort` は、C の `qsort` より**速い**（比較関数がインライン展開されるため）
- クラスのメソッド呼び出しは、ただの関数呼び出しと**同じコスト**（`virtual` でなければ）
- ラムダ式は、関数ポインタより**速い**（これもインライン展開される）

Pythonのように「便利な書き方をすると遅くなる」ということが**ない**。
これがC++を学ぶ最大の見返りです。**抽象化してもタダ**なのです。

```cpp
// これは
std::vector<double> v(1000);
for (auto& x : v) x = 1.0;

// 最適化(-O2)後、これと実質同じ機械語になる
double* p = (double*)malloc(1000 * sizeof(double));
for (int i = 0; i < 1000; ++i) p[i] = 1.0;
// （実際にはさらに memset や SIMD 命令に化ける）
```

安全で読みやすい方を書いても、速度で損をしない。これは本当にすごいことです。

> 🐍 **Pythonとの対比**
>
> Pythonでは「`for i in range(n)` より `numpy` の方が速い」「クラスよりタプルの方が速い」
> のように、**書きやすさと速さがトレードオフ**になります。
> C++では、そのトレードオフがほとんど存在しません。
> 迷ったら**読みやすい方**を選んでください。それが速い方でもあります。

## 1.6 学習コストの現実的な見積もり

嘘をつかずに書きます。Pythonが書ける人がC++を学ぶ場合:

| 段階 | 期間の目安 | 到達点 |
|---|---|---|
| 文法が読める | 1週間 | GitHubのC++コードを眺めて構造が分かる |
| 簡単な関数が書ける | 2〜3週間 | 配列を受け取って計算する関数を書ける |
| 自分のプロジェクトが組める | 1〜2ヶ月 | CMakeでビルドし、クラス設計ができる |

**実務で必要なのは「1〜2ヶ月 + 1週間」の地点まで**です。
そこから先は、必要になったときに学べば十分です。

## 1.7 この章のまとめ

- Pythonが遅いのは、**すべての値がヒープ上の型付きオブジェクト**で、
  **実行時に型を調べる**から
- C++が速いのは、**値をそのままメモリに置き、型はコンパイル時に消える**から
- メモリの**連続性**がキャッシュ効率を生み、さらに数倍の差になる
- C++を使うべきは「ベクトル化できない大量計算」。全部書き換えるのではなく、
  **ホットスポットだけを移植してPythonから呼ぶ**
- モダンC++は、昔のC++より圧倒的に安全で書きやすい
- 抽象化にコストがかからない（ゼロオーバーヘッド原則）ので、
  **読みやすい書き方を選んでよい**
